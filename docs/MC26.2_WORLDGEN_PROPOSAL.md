# Starry Trees 26.2：群系扩充与三维、无限蓝图方案

状态：**群系扩充和无限三维宏区单树已实施**。本文件保留原始有限蓝图方案与决策过程；当前实现详情见 [无限主世界单树方案](INFINITE_SINGLE_TREE_DESIGN.md)。末地仍使用上游系统生成器。

2026-10-06 补充：当前代码将主世界/下界分布半径收紧至 4200/1050 格、球面最小间隙设为 2 格；桥梁改为不跨越半格的采样。三个 `starry_skies:*` 额外维度和客户端天空盒已移除，原版天空的低处黑带暂未处理。下文提到的自定义维度是原设计背景，并非当前交付内容。

## 1. 范围、事实与原则

- 以本地 **Minecraft Java 26.2** 的 `minecraft-merged.jar` 中 `data/minecraft/worldgen/biome/*.json` 为 ID 清单，共 **66** 个原版群系：主世界 55、下界 5、末地 5、技术用途 `the_void` 1。Minecraft Wiki 的[群系分类](https://minecraft.wiki/w/Category:Biomes)用于生态主题和变种关系；Wiki 抓取可能落后于 26.2，因此新增的 `sulfur_caves` 以 [Mojang 26.2 更新说明](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-2)及本地游戏数据为准。
- 现有蓝图只覆盖主世界 9 种、下界 5 种群系。末地当前仍由 Starry Skies 的系统生成器生成，故末地表是**可选的下一阶段**，不是假称现有末地采用蓝图。
- 下面的百分数是**设计权重**，不是 Wiki 中的生成概率。Wiki 提供群系特征，权重由本方案为球体世界玩法制定。一个群系只引用一个 100% 配方；表中同列的多个 ID 各自使用该配方，并不是共同分摊。稀有结构球应另有每大区上限，不能只依赖权重。
- 球体 ID 缩写：`o:xxx` = `starry_skies:overworld/xxx`，`n:xxx` = `starry_skies:nether/xxx`，`e:xxx` = `starry_skies:end/xxx`。只选用目前 26.2 仓库里存在的 configured sphere。主世界所有群系至少给基础建材、木材或替代资源留份额，以避免一个大型群系区无法开局。洞穴、深海和末地的配方可例外，但须通过跨群系交通取得资源。
- 桥梁材料均为 26.2 实际存在的**台阶方块**。同一配色写为 `方块 70/方块 30`，表示按坐标哈希选择；不要用每次区块加载都会变的 RNG。跨群系桥按每个放置位置的群系选择配色，边界可在 8～16 格内做确定性混合。
- 用户所说的“资源包天空色”，在本版本应写入**数据包** `data/minecraft/worldgen/biome/<id>.json` 的 `attributes.minecraft:visual/sky_color`；雾色写 `minecraft:visual/fog_color`。普通 `assets` 资源包不能单独覆盖这两个数值。先以官方 26.2 群系 JSON 为底，只改选定的 visual 字段，保留音乐、天气、粒子、生物与水色等字段。默认维度和 Starry Skies 自定义维度应分别截图验证：下界和末地可能使用维度渲染效果，群系 sky color 未必可见。

### 群系分配的实现约束

1. **不要用当前“温度/湿度/高度三维区间最近邻”来直接塞入 55 个主世界群系。**它区分不了河岸、深浅海、稀有变种、洞穴与高峰，还会让有些群系永远不可达。建议分级选取：先在宏区确定气候带和地貌标签，再生成海岸/河流/山峰/洞穴/稀有点位，最后在该子集里按噪声选具体变种。用 fixed seed 跑 100 个种子，验收 55 个主世界 ID 的可达率与频率；`the_void` 不自然生成。
2. **按三维节点位置判定洞穴群系。**洞穴球可以在地表球正上或正下；当前 `BlueprintBiomeSource` 只按 X/Z 最近球取群系，必须改成三维查询。否则 3D 蓝图里同一列的多个群系互相覆盖。默认原版区块生物群系是四分坐标取样，找最近节点时需换算成方块坐标并使用 Y。
3. 球体与桥梁跨群系时，球体采用节点的预定群系；桥梁在空间内使用最近球或沿边插值的一致规则。避免 `BiomeSource` 回调又依赖正在生成的块，引入循环依赖。
4. 特殊球应该结合地貌约束：`o:treasure/ocean_monument` 仅深海/海洋；`o:treasure/stronghold` 使用全局稀有锚点而非普通轮盘；`e:treasure/end_city` 仅末地高地。`sulfur_caves` 需在低 Y 层、远离新手出生区，并确保硫磺史莱姆相关球确实可刷出生物。
5. 方块“天空色”不等于球体材质，也不等于天空盒纹理。对于原版下界和末地，优先保留其雾和维度效果；如将来改为可见天空盒，再增加自定义渲染适配。
6. 配方只决定**球的品种**，还要有变种几何：`deep_*_ocean` 的水球半径比对应浅海增加约 20～35%，球心降低约 16～32 格，并增加海底神殿的候选资格；`ice_spikes` 提高冰球的纵向伸长率；`eroded_badlands` 增加红砂/陶瓦球的瘦高比例；`windswept_*` 增大露空桥跨距；山麓、雪坡、峰顶按 Y 连续过渡。以上数值只是第一轮调参起点，必须受世界高度和桥梁坡度约束。
7. 现有球体资产尚不能完整复制原版群系生态：例如苍白之园虽有苍白橡木、苍白苔藓球，但没有专门的 Creaking 球；花海没有完整的花卉球。方案先用已存在的球体表达主题，新增球体或生物生成规则需另立任务。不要把“群系 ID 已覆盖”误当作“每个原版特征已实现”。

## 4. 从二维树升级为三维树

现状：采样只在圆盘 `(x,z)`，Delaunay 邻接和 Prim 最小生成树也只看水平距离；Y 是树建好后从根向外传播的小坡度值。因此横向扩得很远，纵向通常只轻微起伏，视觉上近乎单层。把 Y 取值范围调大但仍用二维建图，会得到大量陡峭、不可走的桥，并不会形成有层次的三维树。

### 方案 A：分层森林（改动较小）

- 在可用高度中选 3～4 个重叠层带，例如主世界球心 Y 约 24～96、88～168、160～248、232～296；层间有公共区域，球半径与桥坡度计算要保留上下空间。下界按真实维度边界缩小层数。Y 范围以运行时 `getMinY()`、`getMaxY()` 为准，不把这组示例值写死。
- 每层沿用二维 Poisson + Delaunay + 局部 MST，但锚点先由同一宏区共享种子生成。层内做树，层间以每宏区 2～4 条“树干”桥接，桥接使用 3D 最近候选与最大坡度约束。全图再用并查集去环，得到可遍历的 3D 树或少量可控回环。
- 优点：现有算法、JSON、可视化器复用多；容易先做。缺点：层感较明显，单个层仍近似平面；密度增加时同 X/Z 的球、桥会穿插。适合作为过渡原型。

### 方案 B：真正的三维稀疏树（推荐用于有限地图）

- 在有限世界盒中做 **3D Poisson disk / blue-noise** 候选采样；按“球体外表面至少留 6～12 格”的约束，用空间哈希网格而非全点两两比较。先生成球大小，再决定中心位置，避免大球互撞。
- 为每球建立 3D `k` 近邻图（例如 `k=8～12`）和半径上限；限制水平跨度、竖向差、与球体的碰撞。边代价不只用欧氏距离：`cost = 水平长度 + 1.8×|ΔY| + 危险/水域/拥挤惩罚`。先保证图连通，再从多个出生安全锚点向外求最小代价生成树；需要玩法环线时按低概率补边。
- 球体位置建议使用“宏区层状密度场”：在每个 X/Z 都可取多层球，峡谷可空、山脉可厚；每层宏区至少保留一条主干通道。Y 分布可用混合高斯/分段密度，而非均匀填满，给玩家可辨识的高空、云海、深渊。
- 桥梁要有**可走性契约**：单段坡度上限（例如每 8 水平格升/降 1 格）、最小宽度、头部净空、台阶与护栏策略。无法直接满足坡度时插入螺旋坡道、折线中继平台或垂直交通球；不能用现有单段悬链线硬连几十格高度差。
- 3D 空间索引：球体用 `(cellX,cellY,cellZ)` 哈希或 R-tree；桥梁按穿越的 3D 区域登记，区块生成只取相交边。当前只按 X/Z 的 KDTree 与桥梁 AABB 不够。对每个边做体素包围盒包含桥宽，并用球盒裁剪确保不会穿过非端点球。
- 优点：真正利用高度，视觉连续，适合三维群系。缺点：需要重做采样、碰撞、桥和生物群系空间索引，先做 1/20 尺寸原型测性能。

### 方案 C：生长模型（美术表现优先）

从一个或多个树根向外生长 3D 分支：随机吸引点 + 空间殖民（space colonization）或带惯性的 L-system，枝干落在球间桥上；把生长树投影到可放置球体的点集后修复连通性。大枝代表交通干线，小枝末端有稀有球。可做出强烈的“树冠”形态，但均匀覆盖世界与生存路线较难，需要限制枝条终止、热点拥挤及大跨度空洞。推荐仅作为方案 B 的**形状偏置**，不要单独承担连通性。

### 选择建议

先做 A 的可玩垂直桥原型，验证高度、群系与性能；若目标是最终形态，采用 B，并将 C 的吸引点作为审美层。三维原型至少测：100% 目标区块确定性、球体/桥体无碰撞、从出生球能到达每个大区、平均桥坡度与最坏坡度、群系在不同 Y 同列共存、服务器生成耗时与保存体积。

## 5. 不依赖有限初始蓝图的扩展

Minecraft 的 Y 仍有上下界，X/Z 也有游戏实现的坐标限制；这里的“无限”指**不预先生成整个有限圆盘，探索时可以持续向外、结果由种子确定**。

### 方案 I：按需宏区蓝图（推荐）

1. 以 512×512 或 1024×1024 格为一个宏区。`regionSeed = hash(worldSeed, dimensionId, regionX, regionZ, algorithmVersion)`。访问区块时只构造本宏区及必要邻域的候选节点，不产生全世界 JSON。
2. 全局先定义一个**不随加载顺序变化的宏区骨架**：每宏区有确定的中心锚点，使用哈希选定与相邻宏区的边界端口；每个非原点宏区都必须有一条连向“等级更小”的父宏区的主干边。例如父等级用到原点的 Manhattan 距离严格递减来证明不存在孤岛或环；同等级邻边只能是可选回环。这个约束比“双方随机挑邻居”可靠。
3. 本地在 3D 点集中生成树，并把它接到预先约定的所有端口。跨界桥由端口键 `hash(min(regionA,regionB), max(...))` 决定，**两侧独立计算得到同一边**；为跨界球/桥读取一圈 halo，避免区块边缘断裂或重叠。
4. 按空间单元确定球体及桥梁 ID，顺序无关、线程安全。阶段性结果可按宏区缓存到 `world/starrytrees/regions/`，或完全从种子重算；已生成区块存有最终方块，但缓存可加速重访。记录算法版本、配置哈希、种子和实例 ID，迁移时不能静默用新权重改写旧宏区。
5. 宏区群系由连续气候场确定，边界用共享噪声连续过渡；洞穴群系另由 Y/3D 噪声控制。生态稀有点（村庄/要塞/海底神殿）按更大的 super-region 锚点生成，在宏区之间共享索引并限流。
6. 所有候选节点及边都按稳定的整数 ID 排序后再运行带随机数的步骤，禁止让 `HashSet` / `HashMap` 的遍历顺序决定随机数消耗或蓝图序列化顺序。这样同种子在不同 JVM、重启与线程顺序下才有机会保持一致。

主要风险：随机访问远方宏区时的计算延迟、玩家从新旧算法边界穿越时的接缝、同一边被两侧区块重复写入、服务器并行生成时的状态竞争。实现上要做纯函数“坐标→设计”，世界 IO 与缓存只是加速层。相邻宏区以单一规范边界端口为准。

### 方案 II：完全局部纯函数生成

每个 3D 网格用坐标哈希生成候选球，查询固定邻域决定是否保留（Matérn 式局部剔除）；边也由一对节点 ID 的哈希对称决定。无需保存蓝图，远程随机访问非常方便。但局部规则**不能自然保证全局连通**；必须叠加方案 I 的确定性宏区主干/端口。故它适合作为宏区内部的球体分布层，而不宜单独做整张交通树。

### 方案 III：无限程序生成 + 冻结已访问宏区

采用方案 I 生成新宏区，首次访问即把该宏区的球、桥、群系与算法版本写入小文件。更新模组后已有宏区永不改变，新区域使用新规则；新旧交界用两个版本都能解释的固定“兼容端口”，或创建一次迁移接头。这是长期存档最稳妥的版本策略，但会增加磁盘和迁移工具工作量。推荐作为方案 I 的正式发布形态。

### 迁移与验收

- 现有 `overworld_blueprint.json` / `nether_blueprint.json` 属于旧的有限布局。不能在已有存档里删除它们后换无限算法：已经生成的区块会与新生成区块断开。提供**新世界专用模式**和**旧世界冻结模式**；如确实要迁移，应在旧蓝图边缘建立确定性过渡环，再连接外侧无限宏区。
- 不要通过启动时循环全部宏区来建索引。区块生成时只查询与区块三维体积相交的有限邻域，时间与探索总面积无关。基准目标可先定每个新宏区生成 < 200 ms、远处随机传送无明显长时间卡顿，再根据实际硬件测量调整。
- 自动测试至少包含：固定种子重启前后哈希一致；不同区块加载顺序结果一致；跨宏区端口连通；负坐标与 `floorDiv` 正确；1000 个宏区随机抽样无孤立分支；高 Y/低 Y 边界安全；双线程同时请求相邻区块；老世界的既有区块不被改写。

## 6. 待选择的决策

1. **群系覆盖**：建议主世界 55 + 下界 5 都纳入新蓝图规则；末地 5 保持当前上游系统生成器，等三维主世界稳定再决定是否改成蓝图。`the_void` 始终不自然生成。
2. **三维形态**：A 分层原型（最快见到效果）或 B 真三维稀疏树（推荐最终目标）；C 只作为外形偏置。
3. **世界规模**：先实现有限 3D，再转 I+III 无限宏区；或直接从 I+III 搭基础设施。直接做无限工程量更大，但能避免重新迁移有限图。
4. **旧存档**：建议严格冻结旧蓝图与旧区块，新规则只用于新存档；若要旧存档向外扩展，需要单独做“过渡环”。
